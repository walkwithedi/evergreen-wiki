# Knowledge base client: the knowledge base in the browser

A page in the browser, served from your own computer, for people who do not use a terminal: install the skills, set up a library and tell the agent it exists, back up, roll back, move a library or uninstall, and talk to OpenCode about the libraries: file material, take quick notes, run a health check, ask questions. The page lists the registered libraries, which agents have the skills and whether OpenCode is ready. The questions, previews and safety checks of the management steps are those of `install.py` and `install.py backup|rollback|move|uninstall`; the conversation uses the same skills, registry and OpenCode settings as OpenCode in a terminal, so both can be used side by side.

[中文说明](README.zh-CN.md)

## Files

| File | What it is |
| --- | --- |
| `kb_client.py` | the local server: runs the installer's steps and passes their questions to the page |
| `skills_admin.py` | the Skills section: lists the skills OpenCode reads, backs up, restores, imports and creates the ones that are not the knowledge-base skills |
| `intake.py` | File material run by the client: the skill's scripts for each file, the assistant only for term fixes and placing it, delivery into the library, then the consolidation rounds |
| `auto.py` | automatic intake: watches the drop folder of each library switched on, starts unattended runs of `intake.py` and clears the files from the folder |
| `agent.py` | the conversation: starts `opencode serve` on 127.0.0.1, passes its events to the page and answers the permission requests the client may answer itself |
| `web/` | the page (`index.html`, `app.js`, `style.css`); plain HTML, JavaScript and CSS, nothing loaded from the network |
| `kb-client.desktop` | double-click entry; opens a terminal window that runs `kb_client.py` and the page in the default browser. The same entry is in the top folder of evergreen-wiki |

## Requirements

- Linux desktop, Python 3.8 or newer (standard library only), the whole evergreen-wiki folder: the tool runs `install.py` and the skills two folders up.
- A browser with current JavaScript (`fetch`, `EventSource`), such as a recent Firefox or Chromium.
- For the conversation: OpenCode with a model set up (checked with OpenCode 1.19). Without OpenCode the management steps work and the conversation says why it is off. A model missing from OpenCode's settings file only shows a warning, since the settings may come from elsewhere; whether OpenCode can be used shows when it starts.
- Optional: `pdftotext` (poppler-utils). Without it the assistant reads each PDF whole, which is slower and uses more tokens.

No network is needed. On a computer without one, copy evergreen-wiki-v<version>.zip from [Releases](https://github.com/walkwithedi/evergreen-wiki/releases), unzip it and double-click `kb-client.desktop` in the top folder.

## Use

1. Double-click `kb-client.desktop` (Knowledge base), in the top folder of evergreen-wiki or in this one. The first time, the desktop may ask whether to trust or run it; choose to trust and launch. If double-clicking opens the file as text, open a terminal in this folder and run `python3 kb_client.py`. The page opens in the default browser; the terminal window shows its address.
2. On the left, choose a step:
   - Set up: choose the agent (OpenCode is chosen beforehand, since the conversation on this page uses it), install the three skills, set up a library (kind, folder, scope; a preview comes before anything is written) and write the knowledge-base line into the agent's instructions file. A folder that already holds a library is registered as it is. Run it again to add another library. When Set up has finished, the client restarts the OpenCode it started, so the conversation uses the new skills and line at once (while the assistant is working, once it is done); the conversation goes on.
   - Back up, Roll back, Uninstall: as `install.py backup`, `rollback` and `uninstall` (docs/manual-setup.md, section 6).
   - Graph, under a library: the links between its Markdown files, drawn on the page without loading anything from elsewhere (`GET /api/graph`). Entities, summary files, documents, kept originals (Sources folder) and links to pages that do not exist yet have their own colour; files changed since the client started have a ring, and Only new or changed keeps those and their neighbours. Scroll to zoom, drag to move the view or a file, click a file to list what it links to and what links to it. The same files and folders the skills skip are left out (the archive folder, names starting with an underscore, snapshots and time-stamped old versions), as are links in the spec, which are examples. Opening the library folder in Obsidian gives a fuller graph and backlinks; the page shows the folder with a Copy path button. The line at the end of a batch intake opens the graph too.
   - Move a library, or Move next to a library: pick the folder to move it into; then the move preview and confirmation of `install.py move`.
3. What a step prints appears above its question. Folder questions have a Browse button that opens a folder browser: start from the home folder or a mounted drive, open folders, and choose one. No folder is suggested: the browser opens in the home folder. When the folder already in the answer does not exist yet (changing the folder at the preview, for example), the browser opens at its nearest existing parent and keeps the rest of the path as the new folder's name, so choosing there answers with that folder; clear the name to answer with the folder itself. A library preview is confirmed with choices: Write, Change an item first (then which item), or Cancel; in a terminal, `install.py` asks for the same answers typed.
4. When a step finishes well, its panel folds to its title and result line (Show output opens it again); a cancelled or failed step stays open. When Set up completes what Getting started was missing, that card folds too, once; opened again, it stays open.
5. Cancel this step stops the step at its current question; what was finished stays. Quit stops the client and the OpenCode it started. Closing the page also stops both after a while (`--idle`), unless the assistant is still working or a library has automatic intake on.

### Getting started

A card at the top of the page lists what the conversation needs, each with what to do when it is missing: OpenCode found (Check again looks for it again, the same way as at start, after installing it), OpenCode started (Check again starts it anew after it stopped or fell back to simple mode; a missing model in its settings is shown as a warning here), the three knowledge-base skills installed where OpenCode reads them (its own skills folder, `~/.claude/skills` or `~/.agents/skills`; other skills and other agents do not count), a library set up, and the knowledge-base line in OpenCode's instructions (its `AGENTS.md`, or `~/.claude/CLAUDE.md` while it has none). Set up fixes the last three. A sixth, optional item says whether `pdftotext` is installed. When the first five are done, three example requests appear; a click puts one in the box to edit before sending. The card can be hidden; the page remembers that in the browser. The task buttons above the conversation are off until a library exists. A chip in the top bar, shown at all times, says the same about the knowledge-base skills ("3/3 installed", or which are missing); a click lists where each was found, its version and the folders looked in, with Install them when one is missing. The skill lists reload when Set up, Uninstall or Roll back finishes.

### Conversation

OpenCode is looked for, in this order: `--opencode <path>` (or `KB_CLIENT_OPENCODE`), the program search path, the common install folders (`~/.opencode/bin`, `~/.local/bin`, `~/bin`, `/usr/local/bin`, `~/.npm-global/bin`), and the interactive shell (`bash -ic`), which also finds an `opencode` that `~/.bashrc` defines as a function or alias; such an `opencode` is then always run through `bash -ic`, so what the function does first still happens. Hovering over the OpenCode label at the top shows what was found and how.

When the page opens, the client starts OpenCode in the background (`opencode serve`, listening on 127.0.0.1, in the home folder) and shows what OpenCode prints while it starts; starting can take a while, and the client waits up to `--start-timeout` seconds. Then:

- Type a question or request in the box at the bottom; Enter sends, Shift+Enter starts a new line. A message sent while the assistant works is shown as queued and handled after the current work. Stop ends the assistant's current work.
- The buttons above the conversation: File material and Quick note, each with a line on what it does. Continue intake shows only while an intake has files left, File quick notes (with the count) only while notes wait in a library's notes folder, and Health check and Archive old versions sit under More; these send the skills' own phrases. With more than one library the page asks which one.
- File material is run by the client (`intake.py`, local libraries): after choosing the library and ticking any number of files and folders (hidden ones and the library itself left out, at most 2000 files), the client runs kb-incremental's own scripts for each file in turn: `prep.py scan` (duplicate check by content hash, conversion, cleanup), then asks the assistant, in a new conversation for each file, only for the judgement steps (term fixes in the body file, with no masking: the body stays as it is; the head file with the metadata, and a decision file with partition, topic, type, short title and close-read), checks that answer and asks again with the reason up to three times, runs `prep.py file`, sends a file name already in the index back to the assistant to decide between the next version and another title, and delivers with `package.py preview --run` and `deliver`. A file is marked written only when the delivery went through. A panel above the conversation shows each file (waiting, in progress, written with its name in the library, already in the library, needs you, failed with the reason) and, at the end, the counts and where the files were written. Stop ends the run after the current step; Continue files the rest. Duplicates are skipped by content hash, so choosing the same files again files only what is missing. Files no text could be read from (scans, pictures, unknown formats) are listed for the user, with a button that hands them to the assistant the usual way. The conversation cannot be used while a run is going, and the client does not stop for being idle while one is. Each run works in its own folder `~/.config/evergreen-wiki/intake/<run>/` and saves its state there after every change: if the client stops in the middle (closed, killed, restarted), the next start shows the run as stopped with the files still to do, and Continue intake picks them up. When a run ends, the conversation goes back to the one that was open before it. A finished run's folder is removed after seven days. Google Drive libraries are filed by the assistant as before.
- After the files, the same run consolidates (step Consolidate in the panel): while the library's consolidation queue has files, the client starts one consolidation round of kb-incremental (references/consolidate.md) in a new conversation, reads the queue again (`consolidate.py list`) and goes on, showing the round, the files consolidated, the summary changes and the files left. It ends when the queue is empty, when the queue did not get shorter in two rounds in a row, or after as many rounds as the queue had files plus two, with the reason. With Allow everything on, the run needs nobody from the first file to the last round: the round is told to take the recommended Accept all for the summary changes, and a question card the assistant shows during the run is answered with its recommended option (else its first), each logged in intake.log; the accepted changes are listed in each round's readme, and the old summary files move to the archive folder, so Roll back or the archive undoes them. Without it, each round shows the change list as a question card and waits for the answer; a card waiting for a person (question or permission) does not count against a turn's time limit (20 minutes for a file, an hour for a round). Stop and Continue work for the consolidation too. While a run is going, the panel says that it takes long and can be left alone, and how to open OpenCode in a terminal for other work (not on this library); Open in a terminal is off, since it would join the run's conversation.
- Automatic intake (`auto.py`, local libraries): the switch under a library, after a confirmation, makes a drop folder at the library's top, `_Inbox` (`_待入库` when switched on in Chinese; the underscore keeps it out of searches and the graph), and from then on the client files what is put there without anybody on the page. It looks every minute; a file is taken once it has not changed for two minutes, and a run starts only when the assistant is idle with no card waiting and no step or intake is going (OpenCode is started when it is not running). The run is the same as File material followed by consolidation, with Allow everything switched on for its length and back off at the end; switching Allow everything off during the run stops it. Each file leaves the drop folder as soon as it is done: removed when it was written and its original copied into the library's Sources folder, or when it was already in the library; moved to `Filed/` when it was written without such a copy (the library keeps no originals, or the file is over the size limit); moved to `Not-filed/` (`未处理/`) when it needs a person or failed, and never tried again. A stopped run leaves its files in place and pauses the library until a new file comes. With nothing new, a library whose consolidation queue still has files gets a consolidation-only run, until one ends without emptying the queue. The library card shows the drop folder with Copy path, the files waiting, the last run (when, written, already in the library, needing you, consolidated, the log) and, marked, how many files wait in Not-filed. While any library has it on, the client does not stop for being idle: it runs until Quit or the computer is shut down. The switches and last runs are kept in `~/.config/evergreen-wiki/auto-intake.json`, not in the library. `KB_CLIENT_AUTO_POLL` and `KB_CLIENT_AUTO_SETTLE` (seconds) change the two times.
- Logs: the client writes `~/.config/evergreen-wiki/logs/kb-client-YYYYMMDD.log` (INFO, or the --log-level when lower; kept seven days, readable by the owner only): OpenCode starting, restarting and stopping, each permission request and how it was answered (the kind and the path, cut at 200 characters), each step started and ended, and why the client stopped. Each intake run writes `intake.log` in its folder: every script it ran with its arguments, exit code and the last lines of its output (the scan card without the file's opening text and headings), each message to the assistant and how long the turn took, every decision and why one was not accepted, and the name each file was written under. Logs hold file names and paths, never a file's text. Manage and the intake panel show where the logs are, with Copy path.
- When the assistant asks a question with choices, it appears as a card with the choices; a confirmation it asks for in words is answered in the box.
- New conversation starts a clean one. The page keeps one current conversation; reopening the page or the client picks it up again. Earlier conversations stay in OpenCode and can be opened there.
- When a turn ends, each answer folds its steps into one line ("12 steps (Read 5 · Run a command 6 · Change files 1)", in red with the number that failed); a click opens them. The answer itself stays in view, a subagent's work folds the same way, and a conversation picked up again shows its finished turns folded. The conversation grows with the window.
- What the assistant does is shown as it happens: its steps one line each (reading a file, running a script), its reasoning and the working notes before a step folded into one grey line each (click to read), its answer as normal text. Work it hands to a subagent (OpenCode's own helpers, such as explore) appears indented under "Subagent", with the subagent's own steps, permission requests and questions.
- During an intake a stage bar sits above the conversation: Take stock, Convert, Duplicates and names, Clean up, Compare conclusions, File, Wrap up. The current stage comes from the skill script being run (not from the assistant's wording), with one line on why the step works that way; click a stage for more. For a batch intake, a progress line reads the run's progress file in the library (`GET /api/progress`: counts and group names only): batch n of N, files filed, duplicates, to review. Each finished batch adds a short result line to the conversation, and the end of the run one more. Answers the client gave itself are counted on one foldable line ("Allowed without asking: N") instead of one line each.
- A batch intake goes on across conversations. When the skill stops after a finished batch (its conversation has grown long) and nothing else waits, the page counts down three seconds and then starts a new conversation that says Continue intake, with Cancel to stop it. After Stop, an error, or an automatic round that filed no batch, a Continue intake button does it instead. The material chosen for a run that is still open stays readable without a card in every new conversation (the client reads its paths from the run's progress file). In simple mode File material and Continue intake are off, since the assistant cannot ask there to confirm a batch plan.
- Ideas: the welcome area shows the ideas the knowledge base is built on (an LLM-maintained wiki, evergreen notes, name equals version, the status card, evidence before change, checked rewrites, archive instead of delete, a spec that grows, entities and backlinks, file fast and consolidate after, library first), one card at a time with a line and, on More, a few sentences. It turns every eight seconds, waits while the pointer or the keyboard focus is on it, has Previous, Next and Pause, and does not turn by itself when the system asks for reduced motion. During an intake a one-line version sits under the stage bar; a click shows the next idea.
- Skills, on the left, lists every skill OpenCode reads (its own folder, then ~/.claude/skills and ~/.agents/skills; a name found twice is used from the first, and the other copy is marked not used), with its version, its description and its trigger phrases. Try it puts the first phrase into the box below the conversation; nothing is sent by itself. The three knowledge-base skills come first and have only Upgrade besides Try it: it runs Set up, which replaces the skill's folder with the release this client came with, and it is greyed out (with the version in its tooltip) while the installed version is the same or newer. For any other skill, Change opens a card: what should change (when it is used, what it does, examples, the answer, something else), a sentence or two of detail and tips for a good request; Back up and prepare the request copies the skill's folder to `~/.config/evergreen-wiki/skill-backups/<skill>/<time>/` and then puts the request into the box. Restore (shown once a backup exists) puts a backup back after backing up the current version. Import takes a folder that holds SKILL.md or a zip file: it previews name, description, files and size, refuses a name already in use (never overwrites), a zip with paths outside its folder or links, and more than 500 files or 20 MB, and copies it into OpenCode's skills folder without running anything in it. New skill asks a name and one sentence on what it should do, writes a SKILL.md to fill in, and puts a request to complete it into the box.
- The Knowledge base button beside the title folds and unfolds the knowledge base: the libraries, Manage, the Skills section, the step panel, the stage bar and the knowledge-base items of Getting started. Folded, the page fills the window with a read-only skill list beside the conversation: one line per skill in use (its name and the first sentence of its description; open a line for the whole description and the trigger phrases), knowledge-base skills first, scrolling inside its column, with a filter once there are more than eight. The browser remembers whether it is folded; a running step unfolds it. The page opens unfolded, or folded with `--chat-first`.
- The assistant's answers are shown as Markdown: headings, lists, quotes, tables, rules, inline code, bold, italic and web links. Fenced code blocks are set in a monospace font with a Copy button, and coloured for Python, shell, JavaScript, JSON, YAML, SQL and diff; other languages are shown without colours. Answers are built as page elements, never as HTML, so nothing in them runs. Your own messages stay plain text.
- Open in a terminal opens the same conversation in OpenCode's own interface (`opencode --session=<id>`) in a new terminal window (the first found of x-terminal-emulator, mate-terminal, gnome-terminal, konsole, xterm), with the user's own OpenCode settings. While you continue there, the conversation on the page pauses; reload the page when you are back.

Permissions. Every action of the OpenCode the client starts is set to ask first (`OPENCODE_CONFIG_CONTENT`, for that process only; the user's OpenCode settings are not changed). The client answers "allow once" itself for: reading and changing files inside a registered local library; reading the material chosen for this conversation, the installed skills and the agent's own settings; sending a subagent that only looks things up (explore); running a script of an installed skill (`python3 <skill>/scripts/<name>.py ...`, optionally after one `cd <folder> &&`, with no other shell syntax outside quoted arguments; a double-quoted argument with `$`, a backquote or a backslash is asked); plain `mkdir [-p]` and `cp [-p|-r|-R]` within those places (cp reads from any of them and writes only where writing is allowed), with no wildcards and no `~`; and commands that only read (ls, cat, head, tail, wc, stat, file, du, grep, rg, find without its acting options such as -exec or -delete, pwd, echo, test) joined by `;`, `&&`, `||` or `|`, with at most `2>/dev/null`, only the variables HOME, USER, KB_LIBRARIES and PWD, and every path inside those places. Files and folders whose full path is written in a message count as material chosen for the conversation (read only). The client also keeps a work folder of its own in the system temporary folder, removed when it stops: the task buttons name it in their request ("Work folder: …"), the skills put their copies and output files there, and writing there is allowed like writing in a library. The same rules apply to a subagent's requests. Each such answer is noted in the conversation. Everything else appears as a card saying what the assistant wants to read, change or run, with Deny and Allow this once. When OpenCode says what it would stop asking for (for example every `git` command), the card lists it and adds Always allow: the client passes that answer to OpenCode, which then stops asking for those actions, as in a terminal. The client also keeps that answer in its own state file (kb-client.json) and answers matching requests itself from then on, also after OpenCode or the client starts again; a remembered command pattern covers only a plain command, never one joined to another with `;`, `|` or the like. Manage shows how many answers are remembered, with Clear, which forgets them and starts OpenCode anew so that it forgets them too. The user's OpenCode settings files are not changed. Paths are compared as real paths, so a link out of a library is not allowed.

Allow everything. Allow everything in the conversation header (also Allow everything on this page on each card) asks for confirmation once, then the client answers every request with "allow once" itself, including the cards already waiting, until it is switched off with the same button or the client quits. It covers reloading the page, New conversation and the automatic continuation of a batch intake; it is kept in memory only, never in kb-client.json, and Always allow answers are not touched. Each answer is counted in the conversation like the other automatic ones. Question cards in the conversation still wait for an answer; only a client-run intake answers them itself (see File material). Not available in simple mode.

Simple mode. When OpenCode's server does not start in time or lacks the requests the client uses, the conversation runs `opencode run <message>` once per message instead and says so on the page; in this mode the assistant cannot ask for permission or ask questions on the page. Check again in Getting started tries the server again.

Typed folders that are not absolute are taken from the home folder.

Options: `--lang en|zh` (default: the system language), `--port N` (default: a free port), `--no-browser` (print the address only), `--idle SECONDS` (stop when no page has been open that long and no step is running; 0 never; default 120), `--start-timeout SECONDS` (wait that long for OpenCode to start; default 90), `--opencode PATH` (the OpenCode program to use), `--log-level`. For Set up, the kind of library suggested is work; `--agent <target>` and `--preset life|work` answer those questions in advance and `--descriptions <file>` replaces the skill descriptions, as with `install.py`; a wrapper script or a copy of the .desktop entry can fix them for a group of users. `--simple`: Roll back, Move, Uninstall, the Skills section (the read-only skill list stays) and Clear for remembered answers are hidden, and the client refuses those requests (403); Set up, Back up, the graph and the conversation, including Allow everything, stay. `--chat-first` opens on the conversation, as a browser front end for OpenCode: the knowledge base starts folded (see the Knowledge base button above; the browser remembers this apart from the page without `--chat-first`). Above the conversation are the work folder, a model list and Earlier conversations. The work folder is chosen with the folder browser (the last five are offered again; not the home folder itself, a folder holding it or a system folder); OpenCode starts in it, each folder keeps its own last conversation, and the assistant reads and edits files inside it without a card, while commands (other than read-only ones) and anything outside it still ask. The model list offers the models OpenCode's settings name and applies to the conversation until a new one starts. Earlier conversations lists the main conversations of the work folder, newest first, and continues the one chosen. An edit step has Show the change, the diff of that edit (up to 400 lines). The client keeps no copy of the files the assistant edits: use a folder under version control or one that is backed up.

## Safety

- The server listens on 127.0.0.1 only. The address it opens carries a random token; requests without it, or with another host name, are refused, so other pages in the browser cannot use the server.
- The page talks only to this server; the server talks to OpenCode. OpenCode's own server has no password: any program on this computer that finds its port can use it, as with OpenCode started in a terminal. It listens on 127.0.0.1 only, on a port chosen at start, and stops with the client.
- The client stores the current conversation's id in `~/.config/evergreen-wiki/kb-client.json`, and skill backups in `~/.config/evergreen-wiki/skill-backups/`. It writes into a skills folder only for Import, New skill and Restore, each after its confirmation, and never into a knowledge-base skill's folder.
- One step runs at a time. The folder browser only lists folders and file names, and only inside the home folder and mounted drives (a folder elsewhere can still be typed into the answer); the page's own three files are the only files the server sends; the client itself writes nothing outside what the installer's steps write after their confirmation.

## Checking on a desktop

The unit tests answer the questions over HTTP the way the page does. On a real desktop, check after a change:

1. Double-clicking either entry (the top folder, tools/kb-client) opens a terminal window and the page in the default browser.
2. Set up: the folder browser opens in the home folder (when changing the folder at the preview, at the current answer or its nearest existing parent with the new folder's name filled in), lists mounted drives, and its answer appears in the question; the preview is readable before the confirmation.
3. Move: after the move the page lists the library at its new place, and the agent finds it there after a restart.
4. Uninstall: no library folder is deleted unless picked and the confirmation word typed.
5. Cancel this step stops the step without changing anything further; Quit stops the client and the terminal window closes.
6. Conversation: OpenCode starts and the page says it is ready (note how long it takes); a question about a library is answered from it.
7. File material: tick two folders; the request lists them, no other chooser opens, and the intake runs to its report without the terminal. Reading the material and writing the library ask nothing; an action outside them shows a card.
8. Reopening the page shows the same conversation; New conversation starts a clean one.
9. After Quit, no `opencode serve` process is left (`ps -ef | grep "opencode serve"`).
10. Double-clicking finds OpenCode also when it is set up only for terminals (in `~/.bashrc`); the label at the top says how it was found.
11. A subagent's steps appear indented while it works; explore is sent without a card.
12. Reasoning and working notes are folded; a message sent while the assistant works waits as queued.
13. Open in a terminal opens the same conversation in a terminal window.
14. Set up suggests a work library and OpenCode; right after it, a question about the new library is answered from it without restarting anything; after reopening the client, the skills and libraries are still listed.
15. After Always allow on a card, the same kind of action shows no card again; note whether it is still remembered after quitting and reopening the client.
16. Filing ten files: apart from the plan's confirmation, no card asks about the work folder or about mkdir and cp.
17. Filing more than one batch: the stage bar follows the steps, the progress line counts the batches, each finished batch adds a result line, and the end of the run one more.
18. Graph: opens from a library and from the end of an intake; files filed in this session have a ring; the folder copied with Copy path opens in Obsidian.
19. Originals: in a new work library, a filed Word or PDF file has its copy in Sources/ under the topic file's name; in Obsidian, the original link in the topic file opens it; the graph shows it as an original; a new version moves the old copy to the archive folder.
20. Batch intake of more than a few batches: after a batch the skill stops with, the page continues in a new conversation by itself, reading the material without cards; Cancel and Stop leave a Continue intake button.
21. Getting started: on a computer without the skills or a library, the card shows what is missing and Set up fixes it item by item; Check again after installing OpenCode starts the conversation without restarting the client; the preview of Set up is confirmed with the Write, Change an item first and Cancel choices.
22. Fewer cards: after Set up, the step panel and Getting started fold; listing or reading files in a library or the material with ls, head or grep shows no card; a path typed in a message is read without a card; Always allow is still remembered after quitting and reopening the client, and Clear in Manage forgets it; finished turns fold their steps into one line.
23. Ideas: the cards turn and stop while the pointer is on them; with reduced motion set in the desktop, they stay until Next. Fonts and colours read well in light and dark themes.
24. Skills: Try it fills the box without sending; Change backs up first and fills the box; after the assistant has changed the skill, Restore brings back the earlier version. kb-query has only Try it and Upgrade, which is greyed out right after Set up; listing its folder with ls shows no card.
25. Import a zip of a skill and a folder of another; both appear in the list and work in a new conversation. New skill creates a folder that the request then completes.
26. Allow everything: after confirming, a card already waiting goes away and no further card appears, also after New conversation and reloading the page; the button shows it is on; switching it off or quitting the client brings the cards back.
27. Layout: the Knowledge base button folds the page to the skill list and the conversation and back, and the choice survives reloading; with 15 or more skills the list scrolls inside its column and the filter finds a skill by name or phrase; an answer with headings, a list, a table and code blocks is formatted and coloured in the light and the dark theme, Copy copies a code block, and HTML written in an answer is shown as text.
28.
